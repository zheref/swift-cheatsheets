Observation (iOS 17+) vs ObservableObject

The single biggest modern-SwiftUI talking point.

Modern — @Observable
@Observable
final class Cart {
  var items: [Item] = []
  var isLoading = false
  var total: Decimal { items.reduce(0) { $0 + $1.price } }
}

struct CartView: View {
  @State private var cart = Cart()        // view owns it
  var body: some View {
    List(cart.items) { ... }
    ChildView(cart: cart)                 // plain let, no wrapper needed
  }
}

struct ChildView: View {
  @Bindable var cart: Cart                // only when you need $bindings
  var body: some View { Toggle("Gift", isOn: $cart.isGift) }
}

// Tracks per-property: a view only re-renders if it READ that property.
Legacy — ObservableObject
final class Cart: ObservableObject {
  @Published var items: [Item] = []
  @Published var isLoading = false
}

struct CartView: View {
  @StateObject private var cart = Cart()  // created ONCE
  var body: some View {
    List(cart.items) { ... }
    ChildView(cart: cart)
  }
}

struct ChildView: View {
  @ObservedObject var cart: Cart          // passed in; do NOT create here
  var body: some View { ... }
}

// objectWillChange fires for ANY @Published change -> whole view re-renders.

Identity & lifetime rules

Where most SwiftUI bugs come from.

  • @State initialisers run every body evaluation, but the value is kept — never rely on the initialiser running once for side effects.
  • Creating an ObservableObject with @ObservedObject var vm = VM() recreates it on every render. Use @StateObject.
  • Changing a view's structural identity (branch of if, position in a ForEach) destroys its @State.
  • Give ForEach stable IDs (Identifiable), never array indices for mutable collections.
  • .id(value) deliberately forces a fresh identity — useful to reset a subview.
  • .task(id:) cancels and restarts when the id changes; it's tied to view lifetime.
  • onAppear/onDisappear can fire multiple times (e.g. in NavigationStack); prefer .task for async work.

Async work in a view

struct FeedView: View {
  @State private var items: [Item] = []
  @State private var phase: Phase = .loading

  var body: some View {
    List(items) { ItemRow($0) }
      .task {                              // auto-cancelled on disappear
        do { items = try await api.feed() ; phase = .loaded }
        catch { phase = .failed(error) }
      }
      .refreshable {                       // pull-to-refresh, async by design
        items = (try? await api.feed()) ?? items
      }
      .task(id: selectedCategory) { ... }  // restart when the id changes
  }
}

Performance rules

  • Keep body cheap and pure — it can run many times per frame.
  • Split big views into small View structs so re-render scope stays tiny.
  • Use Lazy* stacks/grids for long content; List already recycles.
  • Avoid AnyView — it erases identity and defeats the diffing engine.
  • Avoid heavy work or Date() inside body.
  • GeometryReader in a stack collapses siblings; prefer .containerRelativeFrame or onGeometryChange (iOS 18).
  • Equatable conformance + .equatable() can short-circuit expensive diffs.
  • Instruments → *SwiftUI* template shows view body counts and cause-of-update.

struct TextViewRepresentable: UIViewRepresentable {
  @Binding var text: String

  func makeUIView(context: Context) -> UITextView {
    let tv = UITextView()
    tv.delegate = context.coordinator
    return tv
  }

  func updateUIView(_ tv: UITextView, context: Context) {
    if tv.text != text { tv.text = text }      // guard against feedback loops

  final class Coordinator: NSObject, UITextViewDelegate {
    let text: Binding<String>
    init(text: Binding<String>) { self.text = text }
    func textViewDidChange(_ tv: UITextView) { text.wrappedValue = tv.text }
  }
}

Interview talking points

  • SwiftUI is declarative + state-driven: you describe *what* the UI is for a given state; the framework diffs and applies changes.
  • Views are cheap value types recreated constantly; the persistent thing is the view *identity* and its attached state.
  • UIKit is imperative + reference-based: you mutate a long-lived view object tree and must keep it in sync by hand.
  • SwiftUI's weak spots: fine-grained scroll control, complex text editing, deep customisation → drop down via Representable.
  • UIKit's diffable data source (NSDiffableDataSourceSnapshot) is the imperative world catching up to SwiftUI's diffing.
  • Both can coexist screen-by-screen; migration is usually leaf-first.

TCA — Core Loop

State - Action - Reducer - Store - Effect. Everything else is composition.

The 5 nouns

Memorise this; every TCA answer starts here.

  • State — a value type holding everything the feature needs to render.
  • Action — an enum of *everything that can happen* (user intent + system results).
  • Reducer — (inout State, Action) -> Effect<Action>. Pure, synchronous, testable.
  • Store — runtime that holds state, runs the reducer, executes effects.
  • Effect — the *only* place async / side effects live. Feeds actions back in.
  • Golden rule: reducers never do async work; effects never mutate state.

Minimal feature

The skeleton you should be able to type from memory.

import ComposableArchitecture

@Reducer
struct Counter {
  @ObservableState
  struct State: Equatable {
    var count = 0
    var fact: String?
    var isLoading = false
  }

  enum Action {
    case incrementTapped
    case decrementTapped
    case factButtonTapped
    case factResponse(Result<String, Error>)
  }

  @Dependency(\.numberFact) var numberFact

  var body: some ReducerOf<Self> {
    Reduce { state, action in
      switch action {
      case .incrementTapped:
        state.count += 1
        return .none

      case .decrementTapped:
        state.count -= 1
        return .none

      case .factButtonTapped:
        state.isLoading = true
        return .run { [count = state.count] send in
          await send(.factResponse(Result { try await numberFact.fetch(count) }))
        }

      case let .factResponse(.success(fact)):
        state.isLoading = false
        state.fact = fact
        return .none

      case .factResponse(.failure):
        state.isLoading = false
        return .none
      }
    }
  }
}

Action naming

Actions describe *facts*, not commands to the store.

Do — user intent + results
enum Action {
  case onAppear
  case saveButtonTapped
  case emailChanged(String)
  case userResponse(Result<User, Error>)
  case timerTicked
}
Don't — imperative / logic-y
enum Action {
  case setLoadingTrue        // that's state, not an event
  case fetchUserAndSave      // two things
  case reloadEverything      // what happened?
  case doTheThing(() -> Void)// not Equatable, untestable
}

Effects cheat list

Everything `Effect` gives you.

return .none                                   // no side effect

return .send(.otherAction)                     // synchronous follow-up (avoid for logic sharing)

return .run { send in                          // async work
  let value = try await api.load()
  await send(.loaded(value))
} catch: { error, send in
  await send(.failed(error))
}

return .merge(.run { ... }, .run { ... })      // run in parallel
return .concatenate(.run { ... }, .run { ... })// run in order

return .run { _ in await analytics.log("x") }  // fire-and-forget

// Cancellation
enum CancelID { case search, timer }
return .run { ... }.cancellable(id: CancelID.search, cancelInFlight: true)
return .cancel(id: CancelID.search)

Debounce & long-running effects

Debounced search + a timer effect started/stopped by actions.

@Dependency(\.continuousClock) var clock

TCA — Composition, Dependencies, Testing

How small features become a big app, and how you prove it works.

Scope: parent embeds child

One `Scope` per child domain, then the parent's own `Reduce`.

@Reducer
struct AppFeature {
  @ObservableState
  struct State: Equatable {
    var counter = Counter.State()
    var profile = Profile.State()
  }
  enum Action {
    case counter(Counter.Action)
    case profile(Profile.Action)
  }

  var body: some ReducerOf<Self> {
    Scope(state: \.counter, action: \.counter) { Counter() }
    Scope(state: \.profile, action: \.profile) { Profile() }

    Reduce { state, action in
      switch action {
      case .counter(.incrementTapped):        // parent can observe child actions
        state.profile.score += 1
        return .none
      case .counter, .profile:
        return .none
      }
    }
  }
}

// View side
CounterView(store: store.scope(state: \.counter, action: \.counter))

Optional & collection children

`ifLet` for optional state, `forEach` for identified collections.

@ObservableState
struct State: Equatable {
  var editor: Editor.State?                        // optional child
  var rows: IdentifiedArrayOf<Row.State> = []      // collection of children
}
enum Action {
  case editor(Editor.Action)
  case rows(IdentifiedActionOf<Row>)

var body: some ReducerOf<Self> {
  Reduce { ... }
    .ifLet(\.editor, action: \.editor) { Editor() }

ForEach(store.scope(state: \.rows, action: \.rows)) { rowStore in

Child → parent communication

Prefer a `delegate` action over the parent snooping on internals.

@Reducer
struct Row {
  enum Action {
    case deleteTapped
    case delegate(Delegate)                  // public API of the child
    enum Delegate: Equatable { case didRequestDelete(Row.State.ID) }
  }

  var body: some ReducerOf<Self> {
    Reduce { state, action in
      switch action {
      case .deleteTapped:
        return .send(.delegate(.didRequestDelete(state.id)))
      case .delegate:
        return .none                          // parent handles it
      }
    }
  }
}

// Parent
case let .rows(.element(id: _, action: .delegate(.didRequestDelete(id)))):
  state.rows.remove(id: id)
  return .none

Built-in dependencies worth knowing

Never reach for the global versions inside a reducer.

  • Date() → use @Dependency(\.date.now)
  • UUID() → use @Dependency(\.uuid) (.incrementing in tests)
  • Task.sleep / Timer → use @Dependency(\.continuousClock) + TestClock
  • Int.random(in:) → use @Dependency(\.withRandomNumberGenerator)
  • @Dependency(\.mainQueue) for scheduler-based code, \.openURL, \.dismiss
  • Override for a subtree: .dependency(\.uuid, .incrementing) on a reducer, or withDependencies { } operation: { }

TestStore — exhaustive testing

Every state mutation and every received action must be asserted.

@Test
func incrementAndFetchFact() async {
  let store = await TestStore(initialState: Counter.State()) {
    Counter()

    $0.numberFact.fetch = { "\($0) is a good number." }

    $0.count = 1                        // assert the *diff* only

    $0.isLoading = true

Tree-based (@Presents) for sheets/alerts, stack-based (StackState) for push navigation.

Pick your navigation style

  • Tree-based — @Presents var destination: Destination.State?. Best for sheets, popovers, alerts, one-off drill-ins.
  • Stack-based — var path = StackState<Path.State>(). Best for arbitrarily deep push navigation.
  • Both make navigation *state-driven*: set state → screen appears. Deep links become State construction.
  • @Presents gives you free dismissal handling: SwiftUI setting the binding to nil sends .dismiss.

Tree-based: sheet / popover / fullScreenCover

One enum reducer for all destinations of a screen.

@Reducer
struct Inventory {
  @Reducer
  enum Destination {                       // @Reducer on an enum = destination reducer
    case addItem(ItemForm)
    case detail(ItemDetail)
  }

  @ObservableState
  struct State: Equatable {
    @Presents var destination: Destination.State?
    var items: IdentifiedArrayOf<Item> = []
  }

  enum Action {
    case addTapped
    case itemTapped(Item.ID)
    case destination(PresentationAction<Destination.Action>)
  }

  var body: some ReducerOf<Self> {
    Reduce { state, action in
      switch action {
      case .addTapped:
        state.destination = .addItem(ItemForm.State())
        return .none

      case let .itemTapped(id):
        guard let item = state.items[id: id] else { return .none }
        state.destination = .detail(ItemDetail.State(item: item))
        return .none

      // Listen to a child action across the presentation boundary:
      case let .destination(.presented(.addItem(.delegate(.saved(item))))):
        state.items.append(item)
        state.destination = nil            // programmatic dismiss
        return .none

      case .destination:
        return .none
      }
    }
    .ifLet(\.$destination, action: \.destination)
  }
}

Stack-based navigation

`StackState` + `NavigationStack(path:)`. Deep links = appending to the path.

@Reducer
struct AppFeature {
  @Reducer
  enum Path {
    case detail(Detail)
    case settings(Settings)
  }

  @ObservableState
  struct State: Equatable {
    var path = StackState<Path.State>()
    var root = Root.State()
  }

  enum Action {
    case root(Root.Action)
    case path(StackActionOf<Path>)
  }

  var body: some ReducerOf<Self> {
    Scope(state: \.root, action: \.root) { Root() }
    Reduce { state, action in
      switch action {
      // React to an action from *any* Detail screen on the stack:
      case let .path(.element(id: id, action: .detail(.doneTapped))):
        state.path.pop(from: id)
        return .none
      case .root, .path:
        return .none
      }
    }
    .forEach(\.path, action: \.path)
  }
}

async / await basics

`await` = a possible suspension point, not a thread hop guarantee.

func loadUser(id: Int) async throws -> User {
  let (data, response) = try await URLSession.shared.data(from: url(id))
  guard (response as? HTTPURLResponse)?.statusCode == 200 else { throw APIError.badStatus }
  return try JSONDecoder().decode(User.self, from: data)
}

// Sequential: total time = a + b
let user = try await loadUser(id: 1)
let posts = try await loadPosts(for: user)

// Concurrent: total time = max(a, b)
async let user  = loadUser(id: 1)
async let stats = loadStats(id: 1)
let (u, s) = try await (user, stats)      // both awaited here

Structured vs unstructured

Interviewers love this distinction.

  • Structured: async let, TaskGroup. Child tasks cannot outlive the scope; cancellation and errors propagate automatically.
  • Unstructured: Task { } — inherits actor isolation + priority, but you must retain/cancel it yourself.
  • Detached: Task.detached { } — inherits *nothing*. Rarely the right answer; only for truly independent background work.
  • Rule of thumb: use structured concurrency; Task { } only at the boundary between sync (e.g. a SwiftUI button) and async code.

TaskGroup — dynamic fan-out

Use when the number of child tasks is only known at runtime.

func thumbnails(for ids: [String]) async throws -> [String: UIImage] {
  try await withThrowingTaskGroup(of: (String, UIImage).self) { group in
    for id in ids {
      group.addTask { (id, try await fetchThumbnail(id)) }   // runs concurrently
    }
    var result: [String: UIImage] = [:]
    for try await (id, image) in group {                     // results in COMPLETION order
      result[id] = image
    }
    return result
  }
}

// Bounded concurrency (don't launch 10 000 tasks):
try await withThrowingTaskGroup(of: Void.self) { group in
  var it = ids.makeIterator()
  for _ in 0..<4 { if let id = it.next() { group.addTask { try await work(id) } } }
  while try await group.next() != nil {
    if let id = it.next() { group.addTask { try await work(id) } }
  }
}

Cancellation

Cooperative: nothing is killed, you must check.

Task.isCancelled                       // non-throwing check
try Task.checkCancellation()           // throws CancellationError

let task = Task {
  for chunk in chunks {
    try Task.checkCancellation()
    await process(chunk)

}
task.cancel()                          // cancels task AND all its children
await task.value                       // await result (rethrows)

  try await longRunningWork()

Actors, Sendable & Isolation

The Swift 6 data-race safety model, and how to talk about it.

actor = reference type with a serial executor

Mutable state protected by the compiler.

actor ImageCache {
  private var cache: [URL: UIImage] = [:]        // isolated: only reachable via await

  func image(for url: URL) -> UIImage? { cache[url] }     // implicitly async from outside

  func insert(_ image: UIImage, for url: URL) { cache[url] = image }

  nonisolated let name: String = "images"        // immutable -> no isolation needed
  nonisolated func describe() -> String { "Cache(\(name))" }
}

let cache = ImageCache()
await cache.insert(image, for: url)              // cross-actor call = await
let img = await cache.image(for: url)

Actor reentrancy — the classic trap

Every `await` inside an actor is a chance for other calls to interleave.

actor Downloader {
  private var cache: [URL: Data] = [:]
  private var inFlight: [URL: Task<Data, Error>] = [:]

  // BUG: two callers can both see an empty cache and both download.
  func badFetch(_ url: URL) async throws -> Data {
    if let hit = cache[url] { return hit }
    let data = try await URLSession.shared.data(from: url).0   // <-- suspension!
    cache[url] = data
    return data
  }

  // FIX: store the *task*, not just the result, before suspending.
  func fetch(_ url: URL) async throws -> Data {
    if let hit = cache[url] { return hit }
    if let running = inFlight[url] { return try await running.value }
    let task = Task { try await URLSession.shared.data(from: url).0 }
    inFlight[url] = task
    defer { inFlight[url] = nil }
    let data = try await task.value
    cache[url] = data
    return data
  }
}

Sendable in one screen

What can safely cross an isolation boundary.

  • struct/enum of Sendable members → implicit Sendable (if not public; public needs explicit conformance).
  • final class with only let Sendable properties → can be Sendable.
  • actor types are always Sendable.
  • Non-final classes and classes with var state are not Sendable.
  • @unchecked Sendable = "I promise I lock correctly." Only with a real mutex/queue inside.
  • @Sendable on closures: no capture of non-Sendable state, no mutable captures.
  • sending parameters (SE-0430) transfer ownership across isolation without needing Sendable.

Sendable conformance

Do
struct User: Sendable {
  let id: UUID
  let name: String
}

final class Counter: @unchecked Sendable {
  private let lock = NSLock()
  private var _value = 0
  var value: Int { lock.withLock { _value } }
  func increment() { lock.withLock { _value += 1 } }
}

@MainActor final class ViewModel { var items: [User] = [] }
// MainActor isolation makes it safe to share.
Don't
final class Counter: @unchecked Sendable {
  var value = 0                 // no lock -> a lie to the compiler
}

class Model: Sendable { }       // non-final: subclass can add mutable state

// Capturing mutable local state in a @Sendable closure
var total = 0
Task { total += 1 }             // error / race

Swift 6 Concurrency — Do's & Don'ts

Migration traps, and how modern code meets legacy GCD/Combine code.

Never block a thread waiting on async

The cooperative thread pool has ~one thread per core. Blocking one can deadlock the app.

Don't
func value() -> Int {
  let sem = DispatchSemaphore(value: 0)
  var result = 0
  Task {
    result = await compute()
    sem.signal()
  }
  sem.wait()          // deadlock risk, priority inversion
  return result
}

DispatchQueue.main.sync { ... }   // from async code: hangs
Do
func value() async -> Int {
  await compute()
}

// At a sync boundary you cannot change, hop instead of block:
Task { @MainActor in
  let v = await compute()
  self.label.text = "\(v)"
}

Don't use queues for mutual exclusion in new code

Do

  • Mark model types Sendable and keep them value types.
  • Put @MainActor on view models / anything touching UIKit or SwiftUI state.
  • Use nonisolated for pure helpers so callers don't need await.
  • Prefer async let / TaskGroup over manually spawned Tasks.
  • Store Task handles you need to cancel (and cancel in deinit / onDisappear).
  • Use Task.sleep, ContinuousClock, or an injected clock instead of Thread.sleep/Timer.
  • Turn on SWIFT_STRICT_CONCURRENCY = complete per-module and migrate incrementally.
  • Use @preconcurrency import to silence a legacy module while you migrate.

Don't

  • Don't use DispatchSemaphore/DispatchGroup.wait() to make async look sync.
  • Don't sprinkle Task { } inside loops — that's unstructured and unbounded.
  • Don't use Task.detached just to "get off the main thread"; a nonisolated async func already does.
  • Don't add @unchecked Sendable to silence errors without a real lock.
  • Don't assume state is unchanged across an await inside an actor (reentrancy).
  • Don't capture self strongly in a long-lived Task on a view controller.
  • Don't resume a continuation twice (crash) or zero times (leak + hang).
  • Don't rely on Thread.current — a task can resume on any thread.

Talking points

Short answers that show depth.

  • GCD threads *block*; Swift concurrency tasks *suspend* and free the thread. That's why blocking a cooperative thread is so bad.
  • await does not guarantee a thread change; it guarantees the correct isolation domain.
  • Thread explosion: 1000 DispatchQueue.global().async calls can spawn ~64+ threads. TaskGroup is bounded by the core count.
  • Priority inversion: GCD needs manual QoS care; Swift concurrency escalates priority automatically for actor/task dependencies.
  • Combine is still the right answer for UIKit-era reactive pipelines and for @Published; new code usually prefers AsyncSequence + Observation.

Combine — Core

Publisher -> Operator -> Subscriber. Output + Failure are part of the type.

Mental model

  • Publisher<Output, Failure> emits 0…n values then either .finished or .failure — never both, never after.
  • Subscriber requests demand (backpressure). sink/assign request .unlimited.
  • A pipeline is inert until subscribed, and dies when its AnyCancellable deallocates.
  • Failure == Never means the compiler knows it can't fail — required by assign(to:on:).
  • .eraseToAnyPublisher() hides the huge generic type at API boundaries.

Combine ↔ async/await bridging

You will be asked how to migrate.

Publisher → async
for await value in publisher.values { ... }

// single value
let user = try await publisher
  .first()
  .values
  .first(where: { _ in true })

// or the common helper:
extension Publisher {
  var firstValue: Output {
    get async throws {
      for try await v in values { return v }
      throw CancellationError()
    }
  }
}
async → Publisher
func publisher<T>(_ op: @escaping () async throws -> T)
  -> AnyPublisher<T, Error> {
  Deferred {
    Future { promise in
      Task {
        do { promise(.success(try await op())) }
        catch { promise(.failure(error)) }
      }
    }
  }
  .eraseToAnyPublisher()
}

Combine gotchas

  • Future is eager — it runs at creation, not at subscription. Wrap in Deferred.
  • Forgetting .store(in:) → pipeline cancelled immediately, nothing happens.
  • assign(to:\.x, on: self) creates a retain cycle. Use sink { [weak self] }.
  • subscribe(on:) affects the *subscription*, receive(on:) affects delivery downstream of it.
  • An error terminates the stream forever. Use catch/replaceError inside a flatMap to keep the outer stream alive.
  • Combine has no built-in backpressure control in sink — it requests unlimited demand.

func withTimeout<T: Sendable>(
  _ seconds: Double,
  _ op: @escaping @Sendable () async throws -> T
) async throws -> T {
  try await withThrowingTaskGroup(of: T.self) { group in
    group.addTask { try await op() }
    group.addTask {
      try await Task.sleep(for: .seconds(seconds))
      throw TimeoutError()
    }
    let first = try await group.next()!
    group.cancelAll()                    // cancel the loser
    return first
  }
}

SwiftUI + Combine — Wiring Them Together

Where Combine plugs into a SwiftUI view, and what replaced it in the Observation era.

The connection points

There are only a handful. Know all of them.

  • ObservableObject + @Published — the object *is* a publisher; SwiftUI subscribes to objectWillChange.
  • .onReceive(publisher) { value in } — subscribe to any publisher for the view's lifetime.
  • assign(to: &$published) — pipe a publisher straight into a @Published property (no cancellable needed).
  • objectWillChange.send() — manual notification when you don't use @Published.
  • .task { for await x in publisher.values { } } — bridge Combine into structured concurrency.
  • With @Observable (iOS 17+) there is no objectWillChange and no @Published; Combine becomes an *input* only.

SwiftUI + Combine pitfalls

  • Building a publisher inside body / onReceive(...) — it is recreated every render. Build it in init or store it in a let.
  • @ObservedObject var vm = VM() — recreated on each render. Use @StateObject (or @State with @Observable).
  • Forgetting .receive(on: RunLoop.main) before touching UI state (or mark the VM @MainActor).
  • An error reaching the outer publisher kills the stream permanently — catch inside the flatMap/map+switchToLatest.
  • assign(to: \.x, on: self) retains self. Prefer assign(to: &$published) or sink { [weak self] }.
  • Nested ObservableObjects don't propagate; forward objectWillChange manually or flatten the model.
  • DispatchQueue.main vs RunLoop.main: RunLoop.main pauses during scroll tracking (often what you want for search); DispatchQueue.main always delivers.
  • New code: prefer @Observable + async/await; keep Combine for debounce/throttle/multi-source merges and legacy APIs.

Clean Code in Swift

The short version

If you can only remember five things.

  • Names reveal intent. A good name removes the need for a comment.
  • Functions do one thing, at one level of abstraction, and are small.

Code smells checklist

Say these names when reviewing code out loud.

  • Long function / god object — many reasons to change, hard to name.
  • Deep nesting — invert conditions and use guard for early exit.
  • Duplicated logic — the third copy is when you extract.
  • Primitive obsession — String for an id/email; use a typed wrapper.
  • Feature envy — a method that mostly touches another type's data; move it.
  • Shotgun surgery — one change forces edits in ten files; the abstraction is wrong.
  • Temporal coupling — configure() must be called before start(); enforce it in the initialiser.
  • Boolean blindness — several Bools that encode one state; use an enum.

Clean tests (F.I.R.S.T.)

  • Fast — milliseconds. No network, no sleeps: inject a clock.
  • Independent — order must not matter; no shared mutable state between tests.
  • Repeatable — inject Date, UUID, randomness. No flakiness.
  • Self-validating — a pass/fail assertion, never manual inspection of a log.
  • Timely — written with (or before) the code.
  • One logical assertion per test; name it test_whenX_thenY. Arrange / Act / Assert structure.

SOLID in Swift

Five principles, one concrete Swift example each. Say the name, then the smell it prevents.

The one-line versions

  • Single Responsibility — a type has one reason to change.
  • Open/Closed — open for extension, closed for modification.
  • Liskov Substitution — a subtype must be usable anywhere its supertype is, without surprises.
  • Interface Segregation — many small protocols beat one fat protocol.
  • Dependency Inversion — depend on abstractions, and let the caller supply them.
  • In Swift, protocols + value types + closures do most of the work; you rarely need class hierarchies.

Functional Programming in Swift

Values, purity, and functions as data — with the standard-library tools that express them.

Core ideas

  • Pure function — same input → same output, no observable side effects. Trivially testable and parallelisable.
  • Immutability — let by default; model changes as new values, not mutations.
  • Value semantics — struct/enum copy on assignment, so no shared-state races.
  • First-class functions — pass, return and store functions like any value.
  • Declarative — describe *what*, not the loop mechanics.
  • Algebraic data types — struct = AND (product), enum = OR (sum). Make illegal states unrepresentable.
  • Swift is multi-paradigm: use FP where it clarifies (transforms, pipelines), not dogmatically.

Laziness, memoization & pure transforms

  .map(expensiveTransform)

// Memoize a pure function
func memoize<A: Hashable, B>(_ f: @escaping (A) -> B) -> (A) -> B {
  var cache: [A: B] = [:]
  return { a in
    if let hit = cache[a] { return hit }
    let value = f(a); cache[a] = value; return value
  }
}

// Pure update on a value type
func updating<T>(_ value: T, _ mutate: (inout T) -> Void) -> T {
  var copy = value; mutate(&copy); return copy
}
let renamed = updating(user) { $0.name = "Ada" }

Trade-offs to mention out loud

  • Pure functions are trivially unit-testable and thread-safe — a natural fit for Swift 6 Sendable.
  • Value semantics remove whole classes of aliasing bugs; SwiftUI and TCA are built on it.
  • Copying large structs can cost; Swift's CoW helps, but measure (isKnownUniquelyReferenced for custom CoW).
  • Deep operator chains can hurt readability and compile times — name intermediate steps.
  • inout and mutating are the pragmatic escape hatch: local mutation, value semantics preserved.

@MainActor @Observable
final class Store<State, Action> {
  private(set) var state: State
  private let reduce: (inout State, Action) -> Effect<Action>

  init(initial: State, reduce: @escaping (inout State, Action) -> Effect<Action>) {
    self.state = initial
    self.reduce = reduce
  }

  func send(_ action: Action) {
    let effect = reduce(&state, action)          // pure, synchronous
    Task { for await next in effect.actions { send(next) } }   // side effects re-enter
  }
}

  switch action {
  case .increment:
    state.count += 1
    return .run { [n = state.count] in .factResponse(await api.fact(n)) }
  case .factResponse(let fact):
    state.fact = fact
    return .none
  }
}

How to answer "which architecture would you use?"

  • Start with the constraints: team size, app lifetime, testing bar, SwiftUI vs UIKit, how much shared state there is.
  • Name the invariants you want: one source of truth, no logic in views, navigation as data, framework-free domain.
  • Then pick the lightest pattern that gives them — usually MVVM + repositories for SwiftUI, TCA when state is genuinely complex.
  • Say what you'd not do: no architecture astronautics on a 5-screen app; no VIPER for a prototype.
  • Mention the seams that matter more than the acronym: DI, a testable domain, and navigation modelled as state.
  • Avoid answering with a single acronym and no trade-off — that is the actual failure mode.

Why modularize at all

Have concrete reasons ready; "cleanliness" is not one.

  • Build times — only the changed module and its dependents recompile.
  • Enforced boundaries — internal is invisible across modules, so architecture becomes compiler-checked.
  • Parallel teams — clear ownership, fewer merge conflicts in one giant project file.
  • Faster feedback — run one module's tests, or launch a tiny preview app for one feature.
  • Reuse — share a design system or networking layer with an extension, watch app, or second product.
  • Cost: more setup, dependency-injection plumbing, resource/bundle handling, and versioning discipline.

Pitfalls

  • A Common/Utils/Shared module everything depends on — it becomes the new monolith and rebuilds constantly.
  • Cyclic dependencies — SPM refuses them; the fix is an interface module or moving the shared type down a layer.
  • Over-modularization — 80 micro-modules cost more in linking and DI wiring than they save.
  • Feature A importing Feature B. Features should be siblings that only meet in the app or via an interface module.
  • Forgetting Bundle.module for resources, or localizing strings in the wrong bundle.
  • Mixing dynamic and static linking carelessly — too many dynamic frameworks slows app launch.
  • Give every module a test target and, ideally, a runnable preview/demo app.
  • Enforce the graph in CI (a dependency-lint step) — documentation alone never holds.

Principles worth stating out loud

  • Test behaviour through the public API, not private implementation — otherwise every refactor breaks the suite.
  • Inject Date, UUID, randomness, the clock and the network. Anything else is a flake waiting to happen.
  • One reason to fail per test; the name should read as a specification: test_whenOffline_showsCachedResults.
  • Prefer fakes over mocks: an in-memory repository survives refactors, a strict mock does not.
  • Snapshot tests are great for design systems, painful for whole screens — scope them tightly.
  • Sleeping in tests (Thread.sleep, wait(for:timeout:5)) — use a TestClock or an injected scheduler.
  • Shared singletons/UserDefaults.standard between tests — parallel execution will find you.
  • Chasing 100% coverage; coverage is a smoke detector, not a goal.
  • TDD in an interview: state the cycle (red → green → refactor) and *actually* write the failing test first if asked.

Core Bluetooth (BLE)

Central role end to end, the GATT model, and the traps that fail interviews.

The connection lifecycle

Every BLE bug is a step done out of order. Left to right, then wrap to row two.

GATT object model

Peripheral → Service → Characteristic → Descriptor. Everything else is detail.

Vocabulary in 8 lines

  • Central — scans, connects, consumes data (usually your iPhone). CBCentralManager.
  • Peripheral — advertises and serves data (the accessory). CBPeripheralManager if *you* are the accessory.
  • GATT — the attribute database exposed by the peripheral; ATT is the wire protocol underneath.
  • Service — a named group of characteristics, identified by a CBUUID (16-bit for adopted, 128-bit for custom).
  • Characteristic — the actual value + its properties (read / write / notify / indicate).
  • Descriptor — metadata about a characteristic; 0x2902 (CCCD) is the notify on/off switch.
  • Advertising packet — ≤31 bytes; carries the local name and service UUIDs you can filter on.
  • MTU — negotiated automatically; maximumWriteValueLength(for:) tells you the real payload size (often 20 or 182 bytes).

Central: setup, scan, connect

The Info.plist key is `NSBluetoothAlwaysUsageDescription`.

import CoreBluetooth

final class BLEClient: NSObject {
  private var central: CBCentralManager!
  private var peripheral: CBPeripheral?          // MUST be retained or it deallocates
  private let hrService = CBUUID(string: "180D")
  private let hrMeasure = CBUUID(string: "2A37")

  override init() {
    super.init()
    // A nil queue means every callback arrives on the MAIN queue.
    central = CBCentralManager(delegate: self, queue: .main,
                               options: [CBCentralManagerOptionShowPowerAlertKey: true])
  }
}

extension BLEClient: CBCentralManagerDelegate {
  func centralManagerDidUpdateState(_ c: CBCentralManager) {
    switch c.state {
    case .poweredOn:     c.scanForPeripherals(withServices: [hrService])
    case .unauthorized:  showPermissionHelp()
    case .poweredOff:    showTurnOnBluetooth()
    default:             break        // .resetting, .unsupported, .unknown
    }
  }

  func centralManager(_ c: CBCentralManager, didDiscover p: CBPeripheral,
                      advertisementData: [String: Any], rssi RSSI: NSNumber) {
    guard RSSI.intValue > -70 else { return }          // ignore far-away devices
    c.stopScan()                                       // scanning drains the battery
    peripheral = p                                     // retain BEFORE connecting
    p.delegate = self
    c.connect(p, options: nil)                         // no timeout: cancel it yourself
  }

  func centralManager(_ c: CBCentralManager, didConnect p: CBPeripheral) {
    p.discoverServices([hrService])
  }

  func centralManager(_ c: CBCentralManager, didFailToConnect p: CBPeripheral, error: Error?) { retry() }

  func centralManager(_ c: CBCentralManager, didDisconnectPeripheral p: CBPeripheral, error: Error?) {
    // error != nil means it dropped; nil means you called cancelPeripheralConnection.
    if error != nil { c.connect(p, options: nil) }     // iOS reconnects when it reappears
  }
}

Peripheral delegate: discover, subscribe, parse

extension BLEClient: CBPeripheralDelegate {
  func peripheral(_ p: CBPeripheral, didDiscoverServices error: Error?) {
    guard error == nil, let services = p.services else { return }
    for service in services {
      p.discoverCharacteristics([hrMeasure], for: service)
    }
  }

  func peripheral(_ p: CBPeripheral, didDiscoverCharacteristicsFor s: CBService, error: Error?) {
    for c in s.characteristics ?? [] {
      if c.properties.contains(.notify)  { p.setNotifyValue(true, for: c) }
      if c.properties.contains(.read)    { p.readValue(for: c) }
    }
  }

  // Fires for BOTH readValue(for:) and every notification.
  func peripheral(_ p: CBPeripheral, didUpdateValueFor c: CBCharacteristic, error: Error?) {
    guard error == nil, let data = c.value else { return }
    switch c.uuid {
    case hrMeasure: bpm = Self.parseHeartRate(data)
    default: break
    }
  }

  func peripheral(_ p: CBPeripheral, didWriteValueFor c: CBCharacteristic, error: Error?) {
    // ONLY called for .withResponse writes.
  }

  func peripheralIsReady(toSendWriteWithoutResponse p: CBPeripheral) {
    drainWriteQueue()          // back-pressure signal for .withoutResponse writes
  }
}

// BLE is little-endian; the first byte is a flags bitfield.
static func parseHeartRate(_ data: Data) -> Int {
  let is16Bit = data[0] & 0x01 == 1
  return is16Bit ? Int(UInt16(data[1]) | UInt16(data[2]) << 8) : Int(data[1])
}

Modern wrapper: delegates → AsyncStream

protocol BluetoothClient: Sendable {
  func scan(services: [CBUUID]) -> AsyncStream<DiscoveredDevice>
  func connect(_ id: UUID) async throws
  func values(for characteristic: CBUUID) -> AsyncStream<Data>
  func write(_ data: Data, to characteristic: CBUUID) async throws
}

// Live implementation bridges each delegate callback:
private var discoveries: AsyncStream<DiscoveredDevice>.Continuation?

func scan(services: [CBUUID]) -> AsyncStream<DiscoveredDevice> {
  AsyncStream { continuation in
    discoveries = continuation
    continuation.onTermination = { [weak self] _ in self?.central.stopScan() }
    central.scanForPeripherals(withServices: services)
  }
}

// One-shot calls use a continuation, keyed so the delegate can resume it:
private var connectContinuations: [UUID: CheckedContinuation<Void, Error>] = [:]

func connect(_ id: UUID) async throws {
  try await withCheckedThrowingContinuation { c in
    connectContinuations[id] = c
    central.connect(peripheral(for: id))
  }
}
// In didConnect:   connectContinuations.removeValue(forKey: p.identifier)?.resume()
// In didFail:      ...?.resume(throwing: error)   // exactly once, always

Traps that fail interviews

  • Not retaining the CBPeripheral — it deallocates and the connection silently dies.
  • Calling anything before .poweredOn. Queue your intent and act in centralManagerDidUpdateState.
  • Assuming peripheral.identifier is stable across devices — it is a per-device, per-app UUID, not the MAC address.
  • Forgetting that didUpdateValueFor serves both reads and notifications; switch on characteristic.uuid.
  • Scanning without a service filter, or never calling stopScan() — battery killer, and required for background scanning.
  • Writing more than maximumWriteValueLength(for:) — the data is silently truncated or the write fails.
  • Ignoring that iOS caches the GATT database; a firmware change may need a Bluetooth toggle or a Service Changed indication.
  • connect(_:) has no timeout. Start your own Task.sleep race and call cancelPeripheralConnection.
  • Serialize commands: BLE has one outstanding operation per connection — use an actor or a command queue.
